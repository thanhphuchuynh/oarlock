An SSH gateway for machines you cannot dial

The gateway reads every keystroke and every byte of output, and can inject its own. That is not a gap. It is the direct cost of the one decision this is built on, and it is stated here before anything else it makes possible.

A real ssh prompt on a device behind NAT, on a cellular APN, or on a customer's LAN — without putting a listener, a host key, or an open port on that device. The gateway is the SSH server. The device only ever dials out. Because the gateway sits in the plaintext, every session can be recorded, and authorisation can be withdrawn while the session is still open.

Reach

The machine is in somebody's living room

A treadmill in a customer's home. A rower on a gym floor behind a router nobody controls. It is Android, frequently on cellular, frequently asleep, and it will never accept an inbound connection. Support still has to reach it, and the usual answers (a VPN on the device, a reverse tunnel nobody audits, a listener on a port somebody will eventually find) all put something on the device that has to be defended.

Two ways to reach one. In persistent mode the agent holds a single outbound connection open and the gateway rings it. In dispatch mode a doorbell — MQTT, a webhook, an exec — wakes the agent, which then dials out for that session only. Both converge on the same code the moment a session opens; the mode only decides how the two ends find each other.

Security

Stated before it is claimed

Terminating SSH at the gateway is what makes recording and mid-session revocation possible, and it is also what puts the plaintext somewhere an attacker could reach. An attacker with code execution in the gateway can read live sessions, replay recordings, mint tickets and open a shell on any device in the fleet. Anyone evaluating this should decide whether that is acceptable before reading anything else.

What follows from accepting it is written down rather than implied: the gateway is treated as the most sensitive service in the deployment, authorisation is checked per action, per device and per target, and it is re-checked every thirty seconds for the life of the session — so a withdrawn grant closes a shell that is already open.

Quickstart

A transcript, not a plan

The gateway and the agent on one machine, an operator key, and a shell. What is printed below is what the terminal prints. 

$ ssh -p 2222 -i ./operator_key treadmill-4821@127.0.0.1
oarlock: waking treadmill-4821…
oarlock: treadmill-4821 · gateway-terminated · this session is recorded
sh-3.2$

The agent refuses to start without either a pinned gateway certificate or an explicit -insecure-skip-pin. Handshake v1 binds the signature to the TLS channel, which a middlebox relaying it cannot reproduce — but both ends still accept v0 by default, because a fleet that will not reconnect is a fleet somebody has to drive to. So pinning is what stands under the downgrade, and an agent that connects unpinned because nobody passed a flag is an agent nobody decided about.
